The TCP Conversation

OSI Layer 4 in depth. How TCP opens, maintains, and closes connections. Every flag explained. Sequence numbers, retransmissions, and the packet signatures of port scanning, SYN floods, and brute force attacks.

OSI Layer 4 - Transport What TCP Does and Why It Exists

In Chapter 02 we followed a packet from browser to web server. But we glossed over an important question: what happens if a packet gets lost on the way? The internet is not a guaranteed delivery service. Routers can drop packets when they are overloaded. Links can be unreliable. Packets can arrive out of order.

TCP (Transmission Control Protocol) is the Layer 4 protocol that solves this problem. It sits above IP (Layer 3) and adds three capabilities that raw IP delivery does not have:

  • Reliability: TCP tracks every byte it sends. If the receiver does not acknowledge receipt within a timeout period, TCP automatically re-sends the missing data.
  • Ordering: TCP numbers every byte with a sequence number. Even if packets arrive out of order, the receiver can sort them correctly.
  • Flow control: TCP uses a window size to control how much data can be in flight at once, preventing a fast sender from overwhelming a slow receiver.

The price of all this reliability is overhead. TCP requires a setup handshake before any data is sent, and a teardown sequence when the conversation ends. Every application that needs reliable delivery uses TCP: HTTP, HTTPS, SSH, SMTP, RDP, FTP. Applications that can tolerate some loss and need low latency use UDP instead: DNS queries, video streaming, VoIP.

Why Layer 4 Matters for Security
Because TCP requires a handshake before data flows, attackers can abuse this mechanism. A SYN flood sends millions of connection requests without ever completing the handshake, exhausting server resources. A port scanner sends SYN packets to probe which ports are open without completing connections. Both attacks are visible at Layer 4 and are detectable by Sophos IPS and Wazuh. SafeLine WAF (Layer 7) never sees these attacks because they operate below the application layer.

TCP Flags: The Control Signals

Every TCP packet contains a set of flags - single-bit fields in the TCP header that indicate the purpose of the packet. Think of flags as the subject line of an envelope: they tell the receiver what to do with the packet before it even opens it.

There are six primary TCP flags. Each is either ON (1) or OFF (0). In Wireshark, an active flag is shown in brackets: [SYN], [ACK], [SYN, ACK], [FIN, ACK], [RST].

Flag Full Name Meaning Normal use Suspicious when...
SYN Synchronise Request to start a new connection. Includes the sender's initial sequence number. First packet of every new TCP connection Mass SYN packets to many ports = port scan. Mass SYN to one port = SYN flood DDoS
ACK Acknowledgement Confirms receipt of data. The acknowledgement number field says how many bytes have been received. Almost every packet after the first SYN carries ACK Missing ACKs after SYN/ACK responses = SYN scan in progress
FIN Finish Polite request to close the connection. Sender has no more data to send. End of a normal connection after data transfer completes Rapid FIN without prior data exchange = connection scanning or probing
RST Reset Abrupt termination. Connection is immediately closed, no cleanup. Rejecting a connection to a closed port, or aborting a broken connection Mass RST packets can indicate firewall drops, IDS interference, or TCP RST injection attack
PSH Push Tells receiver to deliver data to application immediately rather than buffering it. Interactive sessions (SSH, Telnet) where each keystroke should go through immediately Rarely suspicious alone, but PSH+URG combination is unusual
URG Urgent Urgent pointer field is valid - some data in this packet should be processed immediately. Rarely used in modern protocols URG flag set in normal web traffic is unusual and worth investigating
TCP Header: Where the Flags Live
The TCP header is 20 bytes minimum. The flags field is the most important for security analysis. Wireshark shows which flags are set in the Info column of the packet list. The source and destination ports, sequence/ack numbers, and flags together tell you everything about what kind of packet this is.

The Three-Way Handshake

Before any application data is exchanged, TCP requires both sides to agree to open a connection. This is the three-way handshake. It takes exactly three packets and establishes the connection parameters that both sides will use for the rest of the conversation.

The three steps are: SYN (client asks to connect), SYN/ACK (server agrees and asks back), ACK (client confirms). Only after these three packets have been exchanged can application data flow.

The TCP Three-Way Handshake - Every Field Explained
[SYN] Seq=0 (client picks random start number) "I want to connect. My first byte will be #0." Packet 2: SYN/ACK Flags: [SYN, ACK] Seq=0 (server's start), Ack=1 (client's 0+1) "OK. My first byte is #0. I received your byte #0." ACK=client's seq+1 confirms receipt Packet 3: ACK Flags: [ACK] Seq=1, Ack=1 (server's 0+1) "Got it. Connection established." Connection Established - Application Data Can Now Flow HTTP GET / HTTP 200 OK / TLS handshake etc. All packets carry ACK to acknowledge received data continuously
The three-way handshake creates a stateful connection. After Packet 3, both sides know each other's sequence numbers and the connection is open. No application data is transmitted until all three packets have been exchanged successfully. This is what TCP's reliability guarantee relies on.

What Sequence Numbers Do

Sequence numbers are the byte counters that make TCP reliable. Here is how they work step by step:

  1. When a client sends its SYN, it picks a random starting sequence number (e.g. 1000). This is called the ISN (Initial Sequence Number).
  2. Every byte of data the client sends is numbered. If the client sends 500 bytes of HTTP data, the sequence number advances from 1000 to 1500.
  3. The server sends an ACK saying "I received up to byte 1500, send me byte 1501 next." This is the acknowledgement number.
  4. If the server does not send an ACK within the timeout period, the client re-sends the missing data. This is a TCP retransmission.

In Wireshark, retransmissions are highlighted in black with the note "[TCP Retransmission]". A burst of retransmissions means packets are being dropped, either due to network congestion or interference from a security tool.

Closing a Connection: FIN vs RST

TCP connections can end in two ways. The method used tells you a lot about whether the close was normal or abnormal.

Connection Teardown: Clean FIN vs Abrupt RST
A clean FIN close takes four packets and is the normal end of any completed connection. An RST is immediate and can mean: closed port, firewall drop, or IDS termination. In a port scan, you receive RST from closed ports and SYN/ACK from open ones.

Attack Signatures in TCP Flag Patterns

Three major attack types have distinctive TCP flag signatures. Once you know these patterns, you will recognise them immediately in Wireshark and in logs.

Layer 4 Attack TCP SYN Port Scan

A port scan probes which ports are open on a target. The SYN scan (also called half-open scan) is the most common type because it is fast and quiet. The scanner sends a SYN to each port but intentionally never sends the final ACK. This means the connection is never fully established, so many servers do not log it at the application layer.

Why it is detectable at Layer 4: The Sophos IPS engine tracks connection state. A large number of SYN packets from one source IP to many different destination ports on the same host, within a short time window, triggers an IPS signature. Wazuh receives the IPS alert and fires a Wazuh rule.

SYN Scan - TCP Flag Pattern
# For each port the scanner probes: # Open port: handshake starts, scanner immediately sends RST 10.0.2.99 -> 10.0.1.10 : port 22 [SYN] # step 1: probe 10.0.1.10 -> 10.0.2.99 : port 22 [SYN, ACK] # step 2: port is OPEN 10.0.2.99 -> 10.0.1.10 : port 22 [RST] # scanner aborts, never sends ACK # Closed port: immediate RST from server 10.0.2.99 -> 10.0.1.10 : port 23 [SYN] # probe 10.0.1.10 -> 10.0.2.99 : port 23 [RST, ACK] # port is CLOSED # Pattern: this repeats for hundreds of ports within 1-2 seconds # Wireshark filter: tcp.flags.syn==1 and tcp.flags.ack==0 and ip.src==10.0.2.99

Layer 4 Attack SYN Flood DDoS

A SYN flood targets the server's connection table. When a server receives a SYN, it allocates memory for a half-open connection and waits for the final ACK. A SYN flood sends millions of SYN packets without ever sending the ACK, exhausting the server's connection table until it cannot accept new legitimate connections.

Why it is a Layer 4 attack: The attack exploits the stateful connection tracking that TCP requires. It does not need to understand the application (Layer 7) at all. Sophos can mitigate it using SYN cookies, which allow the firewall to respond to SYN packets without allocating connection state until the ACK arrives.

SYN Flood - Log Pattern in Sophos
date=2026-09-20 time=10:52:44 log_type=IPS log_component=Intrusion Prevention log_subtype=Drop signature_id=28200001 signature_msg=TCP SYN Flood src_ip=203.0.113.50 dst_ip=10.0.1.10 dst_port=443 protocol=TCP packets_per_second=18500 # 18,500 SYN packets per second - clearly not legitimate action=Drop

Layer 4Layer 7 Attack SSH Brute Force

SSH brute force is a Layer 4/7 combination. At Layer 4, it looks like rapid, repeated TCP connections to port 22. Each attempt opens a full three-way handshake, exchanges SSH protocol messages (Layer 7), submits credentials, fails, and closes the connection. Then immediately repeats.

Because SSH encrypts the application layer, you cannot see the passwords being tried in Wireshark (unlike plain HTTP). But you can see the repeated connection pattern at Layer 4, and the SSH authentication failure messages appear in the system auth log which Wazuh ingests.

SSH Brute Force - Wazuh Alert
{ "timestamp": "2026-09-20T10:55:14.007Z", "rule": { "id": "5712", "description": "SSHD brute force trying to get access to the system", "level": "10", /* level 10 = significant threat */ "groups": ["authentication_failures", "sshd", "brute_force"] }, "data": { "srcip": "10.0.2.99", /* attacker IP */ "dstip": "10.0.1.10", /* target server */ "dstport": "22", /* SSH port */ "failed_attempts": "47", /* 47 failed logins in the window period */ "user": "root", /* username being attempted */ "last_attempt": "2026-09-20T10:55:13Z" } }
Why SafeLine WAF Does Not See These Attacks
All three attacks above (SYN scan, SYN flood, SSH brute force) operate at Layer 4. SafeLine WAF is positioned in the application layer (Layer 7) and only inspects HTTP/HTTPS traffic. SYN packets and SSH connections are invisible to it. The correct tool for Layer 4 attack detection is Sophos IPS and Wazuh with connection tracking rules.

TCP vs UDP: When to Use Each

TCP's reliability comes with a cost: every connection requires a handshake, every packet requires an acknowledgement, and lost packets cause delays while retransmission happens. For some applications, this overhead is unacceptable.

UDP amplification DDoS is worth understanding as a contrast to SYN floods. An attacker sends a tiny UDP request to an open DNS server with a spoofed source IP (the victim's IP). The DNS server sends a much larger response to the victim. By using thousands of DNS servers simultaneously, the attacker can generate enormous traffic volumes to the victim with minimal effort. This is a Layer 4 attack that Sophos can detect via rate limiting on inbound UDP.

OSI Layer 4 - Transport UDP in Depth

UDP (User Datagram Protocol) is the other Layer 4 protocol. Where TCP sacrifices speed for reliability, UDP sacrifices reliability for speed. Understanding UDP is essential because the most common network activity you will analyse - DNS queries - uses UDP, and some of the most devastating DDoS attacks exploit UDP specifically.

The UDP Header: Only 8 Bytes

The entire UDP header is just 8 bytes. Compare this to TCP's minimum 20 bytes. The reason it is so small is that UDP strips out everything that makes TCP reliable: no flags, no sequence numbers, no acknowledgements, no connection state, no retransmission.

UDP Header vs TCP Header - Size and Field Comparison
UDP has four fields, TCP has at least ten. UDP's simplicity is both its strength (speed) and its weakness (no built-in security). An attacker can craft a forged UDP packet far more easily than a forged TCP connection because there is no handshake to complete.

Which Protocols Use UDP and Why

Why UDP is a Security Risk

UDP's lack of a handshake has two major security consequences:

1. IP spoofing is trivial with UDP. Because UDP has no handshake, an attacker can send a UDP packet with a completely forged source IP address. The target will send the response to that forged IP (the real victim). This is the foundation of all UDP amplification DDoS attacks. With TCP, spoofing is much harder because the handshake requires a response that only the real sender could complete.

2. No connection state means no easy firewall context. Sophos can maintain a state table for TCP connections (it knows SYN started a connection). For UDP, Sophos has to use heuristics - it tracks UDP "pseudo-sessions" based on the same src IP, src port, dst IP, dst port tuple. Any UDP packet that does not fit a recent pseudo-session triggers a stateless firewall rule. This is why UDP-based C2 and tunnelling are harder to detect than TCP-based ones.

QUIC and Firewalls
HTTP/3 uses QUIC over UDP/443. Some older Sophos IPS signatures only check TCP/443 for HTTPS. Attackers can use QUIC tunnels to exfiltrate data over UDP/443 and bypass TCP-based TLS inspection. Sophos has specific QUIC detection rules, but they must be explicitly enabled in the application control policy. Verify in Graylog that UDP/443 traffic is being logged and correlated.

Key Takeaways

  • TCP operates at OSI Layer 4 (Transport). It adds reliability, ordering, and flow control on top of IP's best-effort delivery.
  • The six TCP flags are SYN (connect), ACK (acknowledge), FIN (close politely), RST (close abruptly), PSH (push to app), URG (urgent). The pattern of which flags are set in a stream of packets is the primary way to identify TCP-based attacks.
  • The three-way handshake (SYN, SYN/ACK, ACK) must complete before any application data flows. Attacks that exploit this - like SYN floods and SYN scans - operate purely at Layer 4 and are invisible to Layer 7 tools like SafeLine WAF.
  • A SYN scan sends SYN but never the final ACK. Open ports reply SYN/ACK. Closed ports reply RST. This fingerprints which services are running without completing any connection.
  • A SYN flood exploits connection state tables by sending millions of half-open connections. Sophos mitigates this with SYN cookies. Wazuh alerts on the connection rate spike.
  • SSH brute force is visible at Layer 4 (rapid connections to port 22) and Layer 7 (auth failure messages in /var/log/auth.log). Wazuh rule 5712 fires when the failure threshold is exceeded.
  • UDP is the other Layer 4 protocol. It has an 8-byte header with no flags, no sequence numbers, and no handshake. It is faster than TCP but provides no reliability or connection state.
  • DNS (port 53), DHCP (ports 67/68), NTP (port 123), and Syslog (port 514) all use UDP. HTTP/3 uses QUIC over UDP/443 and can bypass TCP-based firewall inspection if not explicitly configured.
  • Because UDP has no handshake, source IP spoofing is trivial. This makes UDP the foundation of amplification DDoS attacks. Sophos detects these via rate limits and IPS signatures. Alerts are searched in Graylog.
  • Sophos UDP flow logs are shorter than TCP logs - there is no duration field, no tcp_flags field, and no retransmission counter. To find UDP logs in Graylog use: protocol:UDP AND dst_port:53.
