Chapter 04

Wireshark: Reading Packets

How to open, filter, and read packet captures. Identifying seven common attacks directly from raw network traffic. The tool every network analyst needs to know.

Learning Objectives

  • Navigate all three Wireshark panes and understand what each one shows
  • Write capture filters and display filters and explain the difference between them
  • Expand a packet's protocol layers and read every field inside the Ethernet, IP, TCP, and HTTP headers
  • Identify a TCP SYN port scan, SSH brute force, HTTP credential theft, ARP spoofing, directory brute force, HTTPS stripping, and data exfiltration directly from a PCAP
  • Use Follow TCP Stream to read a full conversation between two hosts
  • Export filtered packets and save evidence correctly

What is Wireshark and Why Do Analysts Use It?

Wireshark is a packet capture and analysis tool. It captures every packet that arrives at or leaves your network interface and shows you the raw contents of each one in full detail. Think of it as a recording device for everything that travels across the wire, whether encrypted or not, malicious or benign.

Analysts use Wireshark to answer questions that log files alone cannot answer. A log tells you that a connection happened. Wireshark tells you exactly what was inside that connection, byte by byte. When a log says "user logged in" you cannot tell whether the password was sent securely. When Wireshark shows you the TCP stream, you can see the password in plain text if HTTPS was not used.

Where Wireshark Fits in This Course
You learned in Chapters 01-03 what packets are, how TCP works, and what a three-way handshake looks like in theory. Wireshark is the tool that lets you see all of that in practice. From Chapter 05 onwards, whenever we talk about what a protocol looks like on the wire, you will be able to open a PCAP in Wireshark and see it yourself.

The Three Wireshark Panes

When you open Wireshark and start a capture or open a PCAP file, you see three main areas on screen. Understanding each one is essential before you can analyse anything.

Wireshark Interface Layout
The three Wireshark panes. Pane 1 lists every packet. Pane 2 shows the protocol layers of the selected packet. Pane 3 shows the raw bytes. Click any field in Pane 2 to highlight its bytes in Pane 3.

Capture Filters vs Display Filters

Wireshark has two completely separate filter systems. This confuses beginners because they look similar but work very differently.

Capture filters are set before you start recording. They tell Wireshark which packets to save to disk. Packets that do not match a capture filter are thrown away immediately and are gone forever. Use these when you only care about specific traffic and want to keep file sizes small.

Display filters are applied after packets are already captured. They just hide packets from view without deleting them. You can apply, change, and remove display filters as many times as you want without losing any data. Most analysts work with display filters during investigation.

Reading a Packet: Protocol Layer Dissection

Every packet in Wireshark is broken into layers. These layers match the OSI model from Chapter 01. When you click a packet in Pane 1 and expand it in Pane 2, you are drilling down from the outermost wrapping (Ethernet) to the innermost payload (the actual application data).

Expanding a TCP Packet - All Fields Labelled
Every packet has these same layers. The deeper you drill, the closer you get to the actual application data. If the connection uses HTTPS, the application layer is encrypted and shows as unreadable bytes.

Identifying Attacks in a PCAP

The following patterns each have a distinctive signature in Wireshark. Once you have seen each one, you will recognise it instantly in any capture file.

Attack 1: TCP SYN Port Scan Layer 4 - Transport

Why this layer: Port scanning works by sending TCP SYN packets (Layer 4) to probe which services are listening. It requires no knowledge of the application (Layer 7) and no valid Layer 7 content. Sophos IPS detects it at Layer 4. SafeLine WAF cannot see it because it sits at Layer 7 and never processes raw TCP control packets.

A port scan sends a SYN packet to each port on a target host one after another. The scanner does not complete the three-way handshake (it sends SYN but never sends the final ACK). This leaves a trail of half-open connection attempts across sequential port numbers.

What to look for: Many SYN packets from the same source IP to many different destination ports on the same target, all arriving within a second or two. No ACK packets follow the SYN/ACK responses.

Wireshark Display Filter - Isolate SYN Scan Traffic
tcp.flags.syn == 1 and tcp.flags.ack == 0 and ip.src == 10.0.2.99 # What you see in the packet list (rows abbreviated): 10.0.2.99 -> 10.0.1.10 TCP 54821 > 22 [SYN] # port 22 = SSH 10.0.2.99 -> 10.0.1.10 TCP 54822 > 23 [SYN] # port 23 = Telnet 10.0.2.99 -> 10.0.1.10 TCP 54823 > 80 [SYN] # port 80 = HTTP 10.0.2.99 -> 10.0.1.10 TCP 54824 > 443 [SYN] # port 443 = HTTPS 10.0.2.99 -> 10.0.1.10 TCP 54825 > 8080 [SYN] # port 8080 = alternate web # All from same source, to sequential ports, no ACK after SYN/ACK = SYN scan

Attack 2: SSH Brute Force Layer 4 - Transport Layer 7 - Application

Why these layers: At Layer 4 you see rapid repeated TCP connections to port 22. At Layer 7 the SSH protocol exchanges credentials. Sophos IPS fires on the Layer 4 connection rate. Wazuh fires on Layer 7 auth failure log entries from /var/log/auth.log. SafeLine WAF cannot see SSH at all (it only handles HTTP/HTTPS).

A brute force attack tries many passwords against an SSH login. Each attempt opens a full TCP connection to port 22, exchanges SSH protocol messages, fails authentication, and closes the connection. Then the next attempt begins immediately.

What to look for: Rapid, repeated TCP connections to port 22 from the same source. Each connection is short-lived (a few seconds) and ends with FIN or RST. There may be hundreds of these in a short timeframe.

Wireshark Display Filter - SSH Brute Force
tcp.port == 22 and ip.src == 10.0.2.99 # What you see: many complete three-way handshakes, each lasting ~1-2 seconds 10.0.2.99 -> 10.0.1.10 TCP [SYN] # attempt starts 10.0.1.10 -> 10.0.2.99 TCP [SYN, ACK] # server accepts connection 10.0.2.99 -> 10.0.1.10 SSH Client Hello # SSH negotiation 10.0.1.10 -> 10.0.2.99 SSH Server Hello 10.0.2.99 -> 10.0.1.10 SSH Userauth Request # login attempt 10.0.1.10 -> 10.0.2.99 SSH Userauth Failure # wrong password 10.0.2.99 -> 10.0.1.10 TCP [FIN] # connection closed # ...immediately repeated hundreds of times

Attack 3: HTTP Credential Theft Layer 7 - Application

Why this layer: The credentials exist inside the HTTP request body, which is Layer 7 data. Wireshark can see them because it captures all layers. If HTTPS were used, Layer 6 encryption would make the body unreadable to Wireshark (and to a network-based attacker). SafeLine WAF would see the POST content after TLS decryption. Sophos would only see it with SSL inspection enabled.

If a login form submits over plain HTTP (not HTTPS), the username and password are sent as readable text inside the TCP payload. Wireshark shows this directly.

What to look for: An HTTP POST request to a login URL containing form fields with user credentials in the packet details or TCP stream.

Wireshark Filter + Stream Contents
http.request.method == "POST" # Select the POST packet, right-click, Follow > TCP Stream # You will see the full HTTP conversation including the POST body: POST /login HTTP/1.1 Host: shop.example.com Content-Type: application/x-www-form-urlencoded username=admin&password=SuperSecret99! # The password is visible in full because no HTTPS was used

Attack 4: ARP Spoofing Layer 2 - Data Link

Why this layer: ARP is a Layer 2 protocol. It operates below IP and is used to map IP addresses to MAC addresses on the local segment. Because it is below Layer 3, Sophos firewall (which starts at Layer 3) is completely blind to ARP spoofing. Wazuh can only detect it via a dedicated ARP monitoring agent or Suricata rule, not from standard firewall logs. Wireshark is the tool that can see it because it captures at Layer 2.

ARP spoofing sends forged ARP reply packets claiming that a particular IP address belongs to the attacker's MAC address. Wireshark flags duplicate ARP replies automatically in its Expert Information panel.

Wireshark Filter + What You See
arp # Normal ARP reply (first time seeing IP 10.0.0.1): ARP Reply: 10.0.0.1 is at 11:22:33:44:55:66 # legitimate gateway MAC # ARP spoofing (attacker sends new reply claiming same IP): ARP Reply: 10.0.0.1 is at AA:BB:CC:DD:EE:FF # attacker's MAC - DIFFERENT # Wireshark Expert Info panel shows: [WARNING] Duplicate use of IP address 10.0.0.1 detected # MAC changed from 11:22:33:44:55:66 to AA:BB:CC:DD:EE:FF

Attack 5: Web Directory Brute Force Layer 7 - Application

Why this layer: Directory brute forcing sends valid HTTP GET requests (Layer 7 application data) to probe for hidden paths. The attack uses the application protocol correctly - it is not a TCP-level anomaly. This is why SafeLine WAF is the primary defence: it operates at Layer 7, sees every HTTP request, and can rate-limit the source IP when the 404 rate crosses a threshold. Sophos IPS may catch it via HTTP-specific signatures, but SafeLine is the purpose-built tool for this.

Web scanners like gobuster send hundreds of HTTP GET requests per second, each trying a different URL path from a wordlist. The signature is mass HTTP 404 responses from the same source at extremely high speed.

Wireshark Filter
http and ip.src == 10.0.2.99 # Packet list shows rapid sequential GETs all from same source: GET /.htaccess HTTP/1.1 -> 404 Not Found (0.001s) GET /.htpasswd HTTP/1.1 -> 404 Not Found (0.002s) GET /admin HTTP/1.1 -> 404 Not Found (0.003s) GET /backup HTTP/1.1 -> 404 Not Found (0.004s) GET /config HTTP/1.1 -> 404 Not Found (0.005s) # Speed: 100-500 requests per second. All same User-Agent. # User-Agent header: gobuster/3.6 (visible in packet details)

Attack 6: HTTPS Stripping Layer 6 - Presentation Layer 7 - Application

Why these layers: TLS encryption lives at Layer 6 (Presentation). HTTPS stripping prevents the TLS handshake from happening, so the session stays as plain Layer 7 HTTP instead of upgrading to encrypted Layer 6 TLS. Wireshark detects this because it sees HTTP content where TLS should be. Sophos can detect it via its SSL inspection log (no TLS negotiation on an expected HTTPS port). SafeLine WAF sees the resulting plain HTTP traffic and can alert on unencrypted requests to sensitive endpoints.

HTTPS stripping downgrades a victim's HTTPS connection to plain HTTP. The victim's browser never upgrades to TLS, so there is no TLS Client Hello packet from the victim to the destination. Instead, you see plain HTTP on port 443.

Wireshark Filter - Detect HTTPS Stripping
tcp.port == 443 and !tls # This filter shows TCP connections to port 443 with NO TLS handshake # Normal HTTPS would always start with a TLS Client Hello # If you see plain HTTP text on port 443, HTTPS has been stripped # In the TCP stream you would see: GET / HTTP/1.1 Host: bank.example.com # Plain text on a port that should be encrypted = MITM attack active

Attack 7: Data Exfiltration Layer 4 - Transport Layer 7 - Application

Why these layers: Exfiltration is detectable at Layer 4 via byte volume asymmetry in Sophos flow logs (sent_bytes much higher than recv_bytes) and at Layer 7 via the content of the data being sent. Sophos AppControl logs flag unusual data volumes. Wazuh fires on the volume spike. Wireshark shows the actual data being sent if it is unencrypted. If the exfiltration channel uses HTTPS, only Sophos SSL inspection or a host-based agent can see the content.

Exfiltration is when a compromised host sends large amounts of data to an external destination. The pattern is a session where the internal host sends far more data than it receives, over a sustained period.

Wireshark Filter - Large Outbound Transfers
ip.src == 10.0.1.10 and frame.len > 1000 # Then use Statistics > Conversations to see total bytes per connection # Look for: high sent bytes, low received bytes, unusual destination IP # Normal web browsing: 1-5 KB sent, 50-500 KB received per page # Exfiltration: 50-500 MB sent, 1-2 KB received # Statistics > Conversations > TCP tab example: 10.0.1.10 <-> 185.220.101.45 Sent: 98,442 bytes Received: 1,204 bytes Duration: 44s

Following a TCP Stream

The most powerful Wireshark feature for investigation is Follow TCP Stream. Instead of reading individual packets one at a time, it reassembles the entire conversation between two hosts and shows it as a readable text dialogue.

To use it: right-click any packet in the conversation, hover over Follow, then click TCP Stream. Wireshark opens a new window showing everything sent and received in that connection.

Follow TCP Stream Window - HTTP Login
The TCP Stream window rebuilds the full conversation. Red text is data sent by the client (attacker). Blue text is data sent by the server. In plain HTTP, passwords are readable in full.

Exporting Evidence from Wireshark

After identifying an attack, you need to save the relevant packets as evidence. Never save a screenshot alone - the raw PCAP is the admissible evidence.

What to ExportHowFile FormatWhen to Use
Filtered packets onlyFile > Export Specified Packets > Displayed.pcap or .pcapngInclude only the relevant evidence, not the entire capture
Full captureFile > Save As.pcapngWhen you need to preserve everything for a full forensic review
Specific TCP stream as textFollow TCP Stream > Save As.txtWhen you need the readable conversation for a ticket or report
Packet list as CSVFile > Export Packet Dissections > As CSV.csvFor importing into a spreadsheet or SIEM for further analysis
Evidence Naming Convention
Name exported PCAPs with the incident ID, date (YYYYMMDD), and a brief description. Example: INC-2026-0042_20260920_ssh-brute-force.pcap. This ensures evidence can be found and linked to the correct ticket years later.

UDP Attack Patterns in Wireshark

UDP attacks have completely different signatures from TCP attacks because there is no handshake, no flags, and no connection state. The patterns below cover the three most common UDP-based attacks you will encounter. Each one includes the Wireshark filter, what the traffic looks like, and how each tool in the stack detects and mitigates it.

UDP Attack 1: DNS Amplification DDoS Layer 4 - Transport

DNS amplification is one of the most effective DDoS techniques. The attacker sends a small DNS query (typically 60-100 bytes) to an open DNS resolver, but forges the source IP address to be the victim's IP. The DNS resolver sends its large response (often 3000+ bytes) to the victim. By coordinating thousands of DNS resolvers simultaneously, the attacker can generate traffic volumes that overwhelm the victim's uplink without needing much bandwidth themselves.

The amplification factor: A small ANY or DNSSEC query can produce a response 50-100x larger. Sending 1 Mbps of queries can generate 50-100 Mbps of attack traffic aimed at the victim.

Wireshark Filter - Detect Outbound DNS Amplification (your server being used)
udp.port == 53 and udp.length > 500 # Normal DNS response: 50-200 bytes # Amplification response: 1000-4096 bytes (ANY or DNSSEC queries) # What you see - one tiny query generates a huge response to a spoofed IP: # Request (60 bytes, source IP is spoofed = the victim): 203.0.113.99 -> 10.0.1.5 UDP ANY? attacker.com # src=victim's spoofed IP # Response (3,180 bytes sent to the VICTIM, not the real requester): 10.0.1.5 -> 203.0.113.99 UDP 3180 bytes # your server is now part of the attack # Wireshark Statistics > IO Graph: DNS response bytes spike = amplification in progress
ToolWhat it seesDetectionMitigation
Sophos Firewall High volume of outbound UDP/53 responses to many different external IPs. IPS engine sees DNS response rate exceeding threshold. IPS signature "DNS Amplification Attack". Sophos flow logs show dst_ip changing rapidly with large recv_bytes on UDP/53. Enable DNS rate limiting in Sophos DoS policy. Restrict recursive DNS to internal IPs only. Block ANY query type. All alerts searchable in Graylog.
Wazuh Sophos IPS alert forwarded via syslog. Rule fires on high-volume DNS response pattern. Wazuh rule group "dos" fires. Alert level 12+. Graylog receives the Wazuh JSON alert for correlation with Sophos logs. Wazuh active response can trigger a firewall block rule automatically when DNS flood threshold is crossed.
Grafana VM/container network egress metrics spike. DNS query rate metric (from node exporter) spikes dramatically. Grafana alert rule: "DNS egress bytes per second exceeds 10MB/s for 30 seconds". Fires to alerting channel. Grafana does not block traffic, but its alert provides the earliest warning before logs arrive in Graylog.
SafeLine WAF Nothing. DNS is UDP Layer 4. SafeLine only inspects HTTP/HTTPS Layer 7 traffic. No detection. Not applicable for this attack type.

UDP Attack 2: UDP Flood Layer 4 - Transport

A UDP flood sends a massive volume of UDP packets to random ports on a target host. The target has no services listening on most ports, so for each packet it must send back an ICMP "Port Unreachable" response. This consumes CPU and bandwidth on both sides. At high volume, the target's uplink and CPU are saturated.

Unlike DNS amplification, a UDP flood does not require spoofing - the attacker simply floods the target directly. But the attack is traceable because the source IP is real.

Wireshark Filter - UDP Flood Detection
udp and ip.dst == 10.0.1.10 # What you see: massive volume of UDP packets to random high ports 203.0.113.50 -> 10.0.1.10 UDP dest port: 31447 60 bytes 203.0.113.50 -> 10.0.1.10 UDP dest port: 19284 60 bytes 203.0.113.50 -> 10.0.1.10 UDP dest port: 52318 60 bytes # Ports are random each time. Payload is garbage/random data. # Packets arrive at 10,000+ per second # The target responds to each with ICMP Port Unreachable: 10.0.1.10 -> 203.0.113.50 ICMP Port Unreachable # this doubles the network load # Statistics > IO Graph in Wireshark: packets/sec spikes vertically # Statistics > Conversations > UDP: one source IP dominates the table
ToolWhat it seesDetectionMitigation
Sophos Firewall Inbound UDP flood from external IP. IPS sees packets per second to random ports exceeding DoS threshold. Sophos IPS drops the traffic at the perimeter before it reaches the server. IPS signature "UDP Flood". Sophos DoS policy fires. Log: log_type=IPS signature_msg="UDP Flood" action=Drop. Searchable in Graylog: log_type:IPS AND signature_msg:"UDP Flood". Sophos DoS policy: set UDP flood threshold (packets/sec). Enable SYN cookies for TCP and UDP flood protection. GeoIP blocking can reduce attack surface.
Grafana Network ingress bytes on the target VM spike sharply on the Grafana dashboard. CPU metric also rises (ICMP generation). Grafana alert: "inbound network bytes/sec exceeds 500MB for 60 seconds". Fires immediately - often before Graylog processes the log volume. Grafana alert triggers on-call notification. Analyst checks Graylog for the source IP and blocks it in Sophos.
Wazuh If the flood overwhelms Sophos and reaches the host, Wazuh agent sees the kernel log "possible UDP flood" and the ICMP error rate in netstat output. Wazuh rule monitors /var/log/kern.log for flood indicators. Active response can add a host-level iptables drop rule for the source IP. Wazuh active response: add iptables rule dropping traffic from flood source. This is a last-resort host-level block when the perimeter firewall is overwhelmed.

UDP Attack 3: DHCP Starvation Layer 2 - Data Link Layer 4 - Transport

DHCP starvation is an attack against your DHCP server. The attacker sends thousands of DHCP DISCOVER requests, each using a different spoofed MAC address. The DHCP server believes each request is from a different new device and assigns it an IP address lease. Eventually the entire IP address pool is exhausted. New legitimate devices cannot get an IP address and are locked off the network.

This is a Layer 2 attack at its foundation (spoofed MAC addresses) delivered over Layer 4 UDP. A variant is DHCP spoofing - the attacker also runs a rogue DHCP server that responds first, handing out a fake gateway IP and pointing DNS at an attacker-controlled server. All victim traffic then flows through the attacker.

Wireshark Filter - DHCP Starvation Detection
udp.port == 67 or udp.port == 68 # Normal DHCP traffic: a few DISCOVER packets from real MAC addresses # Starvation attack: hundreds of DISCOVER packets per second, all different source MACs # What you see in the packet list: DHCP DISCOVER src MAC: AA:BB:CC:00:00:01 "What is my IP?" DHCP DISCOVER src MAC: AA:BB:CC:00:00:02 "What is my IP?" DHCP DISCOVER src MAC: AA:BB:CC:00:00:03 "What is my IP?" # Hundreds of these per second. All different MACs. All from attacker's real port. # DHCP server exhausted - legitimate device gets no response: # Device sends DHCP DISCOVER, no DHCP OFFER comes back = no IP address assigned # Wireshark filter to spot the pattern: count unique Ethernet source MACs in DHCP traffic # Statistics > Endpoints > Ethernet: many hundreds of unique MACs in a short timeframe
ToolWhat it seesDetectionMitigation
Sophos Firewall Sophos operates at Layer 3 and above. It does not see raw Layer 2 MAC address manipulation. DHCP traffic (UDP/67-68) passes through unless a specific DHCP inspection rule is configured. Sophos can log high-volume DHCP traffic: protocol:UDP AND dst_port:67 in Graylog shows the rate spike. But Sophos cannot see the MAC spoofing directly. Enable DHCP snooping if Sophos is acting as the DHCP relay. Configure the Sophos DoS policy to rate-limit UDP/67. Network switch port security (MAC address limit per port) is the primary control.
Wazuh If a Wazuh agent runs on the DHCP server, it ingests the DHCP server log and sees the lease exhaustion pattern. Rule fires when the lease pool drops below a threshold. Wazuh rule for DHCP log: "DHCP pool near exhaustion" or "DHCP DISCOVER flood from multiple MACs". Alert level 10+. Wazuh active response can trigger a script that flushes stale leases or alerts the switch to enable port security on the offending port.
Grafana Grafana sees the downstream effect: devices failing to get IPs start showing connectivity failures. Container/VM network interface errors increase. DHCP server CPU spikes on the Grafana dashboard. Grafana alert: "DHCP server CPU exceeds 80% for 60 seconds" or "network error rate spike on DHCP server VM". Grafana alert notifies on-call. Analyst investigates Wazuh DHCP logs and Graylog Sophos logs to confirm the attack source port and VLAN.
Primary control Network switch port security - not a software tool in this stack. Configure a maximum of 1-3 MAC addresses per switch port. Any port sending more than the limit gets automatically shut down or placed in violation mode. DHCP snooping on managed switches: only designated "trusted" ports (uplinks, DHCP servers) can send DHCP OFFERs. Untrusted ports can only send DISCOVER/REQUEST. This stops both starvation and DHCP spoofing.
Tool Coverage Summary for UDP Attacks
Sophos IPS is your primary defence against DNS amplification and UDP floods. Grafana gives you the earliest warning via metric spikes before logs are processed. Wazuh catches host-level impact and can auto-block via active response. SafeLine WAF is irrelevant for all three attacks. DHCP starvation requires network switch port security as the primary control - none of the software tools in this stack can fully prevent it alone. All Sophos and Wazuh alerts are searchable in Graylog.

Key Takeaways

  • Wireshark has three panes: Packet List (one row per packet), Packet Details (protocol layers expanded), and Packet Bytes (raw hex). Click a field in Details to highlight it in Bytes.
  • Capture filters drop packets permanently before saving. Display filters just hide packets from view. Always use display filters during investigation so you cannot accidentally lose evidence.
  • Every packet has layers: Ethernet (MAC addresses), IP (logical addresses), TCP (port numbers and connection state), and optionally an application layer (HTTP, SSH, DNS). Each layer wraps the one above it.
  • A TCP SYN scan looks like many SYN packets to sequential ports with no follow-up ACK. SSH brute force looks like many rapid, short-lived TCP connections to port 22. HTTP credential theft shows plaintext username and password in the POST body of the TCP stream.
  • Follow TCP Stream (right-click any packet in a connection) is your single most powerful investigation tool. It shows the complete readable conversation between two hosts in one window.
  • Always export the raw PCAP as evidence. A screenshot is not admissible evidence. The PCAP file contains the complete packet data with timestamps.
  • UDP has no handshake and no flags. Source IP spoofing is trivial, which makes UDP the foundation of amplification DDoS attacks. Sophos IPS detects them via rate limits. Alerts are searched in Graylog.
  • DNS amplification: small spoofed query generates a large response sent to the victim. Sophos rate-limits outbound DNS responses. Grafana detects the egress spike first.
  • UDP flood: mass UDP to random ports forces ICMP Port Unreachable responses, saturating the target. Sophos DoS policy drops the flood at the perimeter. Grafana sees the network ingress spike. Wazuh provides host-level active response as a last resort.
  • DHCP starvation: spoofed MAC addresses exhaust the DHCP pool. Sophos cannot see Layer 2 MAC spoofing. Network switch port security (DHCP snooping) is the primary control. Wazuh catches it via the DHCP server log.
