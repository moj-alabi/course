Reading Logs Like an Analyst

Log anatomy, common formats, pattern recognition and side-by-side field reference tables for Wazuh, Sophos and SafeLine. The skill that ties every chapter together.

Learning Objectives

  • Identify the universal components of any log line: timestamp, host, severity, message
  • Read and parse four common log formats: syslog, JSON, CEF and key=value

The Anatomy of Any Log Line

Every log line ever written, no matter what system produced it, contains a small set of fundamental pieces of information. Once you learn to spot these pieces you can read any log from any tool without needing to look up documentation.

Universal Log Line Anatomy
Every log line has these five components in some form. Learning to extract them quickly is the core skill of log analysis.

The Four Common Log Formats

Different tools write logs in different formats. You will encounter all four of these in your environment. Once you know the structure of each, you can parse any of them mentally in seconds.

1. Syslog (RFC 5424)

The standard Unix/Linux log format. Used by operating systems, SSH, cron, authentication systems, and network devices. Wazuh agents collect syslog from managed hosts.

# Format: <PRI>VERSION TIMESTAMP HOSTNAME APP-NAME PROCID MSGID MSG <34>1 2026-09-20T10:05:33.411Z web-server-01 sshd 4421 - - Failed password for admin from 10.0.2.99 port 54821 ssh2 # Breaking it down: # <34> = Priority: facility 4 (auth) * 8 + severity 2 (critical) = 34 # 1 = Syslog version # Timestamp in ISO 8601 UTC format # web-server-01 = hostname that generated this log # sshd = application name # 4421 = process ID # MSG = the actual event message

2. JSON (Structured)

Modern tools including Wazuh write alerts in JSON. Every field has a name and a value, making them easy to query programmatically and in dashboards.

{ "timestamp": "2026-09-20T10:05:33.411Z", "rule": { "id": "5710", "description": "SSH authentication failed", "level": 5 }, "agent": { "name": "web-server-01", "ip": "10.0.1.10" }, "data": { "srcip": "10.0.2.99", "dstuser": "admin", "dstport": "22" } } # JSON is easy to filter: data.srcip == "10.0.2.99" and rule.level >= 5

3. CEF (Common Event Format)

Used by SIEM vendors and security appliances (ArcSight, some Sophos exports). Fields are pipe-delimited in the header, then key=value in the extension.

# Format: CEF:Version|Device Vendor|Device Product|Device Version|SignatureID|Name|Severity|Extension CEF:0|Sophos|XGS Firewall|20.0|18487|TCP SYN Port Scan|8|src=10.0.2.99 dst=10.0.1.10 spt=45231 dpt=22 proto=TCP act=Drop # Severity: 0-3 Low, 4-6 Medium, 7-8 High, 9-10 Very High # Extension fields: src, dst, spt=src port, dpt=dst port, act=action

4. Key=Value (Sophos Native Format)

Sophos firewall logs use a flat key=value format. Every field is a name=value pair separated by spaces.

date=2026-09-20 time=10:22:14 device_name="SophosXGS-HQ" log_id=010302600001 log_type="IPS" log_subtype="Drop" signature_id=18487 signature_name="TCP SYN Port Scan" severity="High" src_ip=10.0.2.99 dst_ip=10.0.1.10 src_port=45231 dst_port=22 # Parsing: split on spaces, then split each token on first "=" sign # Quoted values: read from opening quote to closing quote

Side-by-Side Log Field Comparison: Wazuh, Sophos, SafeLine

The same event (an SSH brute-force attack) produces different log entries in each tool. Here is what each tool reports and how the fields map to each other.

Scenario: SSH Brute Force from 10.0.2.99 to 10.0.1.10

Wazuh Alert (JSON) - SSH brute force detected by agent on target host
{ "timestamp": "2026-09-20T10:22:14.412Z", "rule.id": "5712", "rule.description": "SSHD brute force trying to get access to the system", "rule.level": 10, "agent.name": "web-server-01", "agent.ip": "10.0.1.10", "data.srcip": "10.0.2.99", "data.dstuser": "admin", "data.dstport": "22" }
Sophos Firewall Log (key=value) - same attack, seen at network perimeter
date=2026-09-20 time=10:22:14 log_type="Firewall" log_subtype="Allowed" src_ip=10.0.2.99 dst_ip=10.0.1.10 dst_port=22 protocol=TCP sent_bytes=412 recv_bytes=880 # Sophos allowed it through - the brute force traffic itself looks like normal TCP to port 22 # Sophos only sees network-level info. It cannot see the SSH authentication failures inside the session.
Wazuh Syslog (raw, before parsing) - from the SSH daemon itself
Sep 20 10:22:14 web-server-01 sshd[4421]: Failed password for admin from 10.0.2.99 port 54821 ssh2 Sep 20 10:22:15 web-server-01 sshd[4421]: Failed password for admin from 10.0.2.99 port 54822 ssh2 Sep 20 10:22:16 web-server-01 sshd[4421]: Failed password for admin from 10.0.2.99 port 54823 ssh2 # Wazuh agent reads these lines in real time, matches rule 5710 (single fail) then 5712 (brute force) # after 8+ failures in 60 seconds, and fires a level-10 alert

The Three-Step Investigation Method

When an alert fires, apply this method consistently before drawing any conclusions. It works for every alert from every tool.

Three-Step Alert Investigation Process
Orient, Scope, Act. Apply this every time before touching any tool or escalating any alert.
Incident Response: Correlating Across Tools
The power comes from using all three tools together. Wazuh fires an SSH brute-force alert at level 10. You go to Sophos flow logs and filter by that source IP to see what other connections it made. You find it also made HTTPS connections to two internal servers. You check SafeLine WAF logs for that same IP and find ten blocked SQLi attempts an hour earlier. Now you have the full picture: recon via web scanning, attempted SQL injection, pivot to SSH brute force. One ticket, three data sources, complete picture.

Key Takeaways

  • Every log line has five universal components: timestamp, hostname, severity, process, and message. Extract these first on any unfamiliar log.
  • The four formats you will encounter are syslog (Unix/Linux), JSON (Wazuh alerts), CEF (SIEM integrations), and key=value (Sophos). Each is parseable with a simple mental rule.
  • The six attack patterns to recognise: brute force (repeated failures same source), directory scan (many 404s same source), port scan (many ports same target), exfiltration (large sent_bytes to unknown external), C2 beaconing (periodic DNS queries same interval), lateral movement (one source authenticating to many internal hosts).
  • Sophos, Wazuh and SafeLine report the same events with different field names. The field mapping table in this chapter lets you translate between them.
  • Always Orient (who, where, when), then Scope (what else happened), then Act (block, isolate, document). Never skip straight to acting on the first alert you see.
