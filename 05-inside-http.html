Chapter 05

Inside HTTP

Requests, responses, methods, status codes, headers, cookies and sessions. The protocol that attackers love most, and what SafeLine WAF and Wazuh see in every exchange.

Learning Objectives

  • Describe what HTTP is and why it is the primary attack surface for web applications
  • Read an HTTP request and identify all its components: method, path, headers, body
  • Read an HTTP response and understand status codes, headers, and body
  • Explain how cookies establish and maintain sessions
  • Identify suspicious HTTP patterns in SafeLine WAF logs and Wazuh web logs
  • Recognise the HTTP fields that appear in SafeLine WAF log entries

What is HTTP?

HTTP (HyperText Transfer Protocol) is the language that web browsers and web servers use to communicate. Every time you load a page, submit a form, log into an application, or click a button on a website, your browser is sending one or more HTTP requests and receiving HTTP responses back.

HTTP is a text-based, stateless protocol. Text-based means the headers are human-readable. Stateless means the server treats every request independently - it does not remember you from one request to the next. Sessions and cookies (explained below) were invented to work around this limitation.

From a security perspective, HTTP is the most important protocol to understand. The vast majority of attacks targeting organisations today happen over HTTP or HTTPS. SQL injection, cross-site scripting, directory traversal, credential stuffing, API abuse and more all arrive as HTTP requests. SafeLine WAF sits in front of your web applications and inspects every one of those requests.

Anatomy of an HTTP Request

An HTTP request has three parts: a request line, headers, and an optional body. Each part carries different information.

HTTP Request Structure - Annotated
Every HTTP request has a method, a path, headers, and optionally a body. SafeLine WAF inspects all components for attack patterns.

HTTP Methods

The method tells the server what action to perform. Attackers use these methods in specific ways, which is why they appear in WAF and web server logs.

MethodPurposeHas BodySecurity Notes
GETRetrieve a resourceNoShould never change server state. Parameters in the URL are fully visible in logs.

PATCHPartially update a resourceYesAPI method. Often less validated than POST.
DELETERemove a resourceNoShould require strong authentication. Unauthenticated DELETE = critical vulnerability.

HEADLike GET but no body returnedNoUsed by scanners to probe without downloading content.

Anatomy of an HTTP Response

The server sends back a response for every request. The most important part of the response from an investigation standpoint is the status code. Status codes are three-digit numbers that tell you exactly what happened. Learning the common ones lets you read access logs at a glance.

HTTP Response Structure
The server's response carries a status code, headers, and a body. Security headers in the response tell you how well-hardened the application is.

HTTP Status Code Reference

Status codes are grouped by their first digit. Knowing the ranges lets you interpret an access log entry instantly.

CodeMeaningAnalyst Significance

301 / 302RedirectClient is redirected. Open redirects can be abused for phishing.

Incident Response: Reading Status Codes in Context
A pattern of 401, 401, 401, 401, 200 from the same source IP on a login endpoint is a brute-force attack that eventually succeeded. A pattern of 404, 404, 404 on paths like /admin, /.env, /config.php, /wp-login.php is directory enumeration. Both patterns are clearly visible in SafeLine WAF access logs.

Cookies and Sessions

Because HTTP is stateless, applications use cookies to maintain session state. When you log in successfully, the server generates a unique session token, stores it on the server side linked to your account, and sends it to your browser as a Set-Cookie response header. Your browser automatically includes that cookie in every subsequent request to the same domain.

The server compares the cookie value against its session store to identify you without asking you to log in again for every page load.

How Cookies Establish and Maintain a Session
The session cookie is set on first login and sent automatically with every request. SafeLine WAF sees the cookie in every request header it inspects.
Session Hijacking
If an attacker steals a valid session cookie, they can impersonate the user without knowing the password. This is called session hijacking. In Chapter 15 (Bettercap MITM), you will see how an attacker can capture session cookies from unencrypted HTTP traffic. Cookie security flags like HttpOnly and Secure reduce but do not eliminate this risk.

Wazuh Web Access Log Fields

When a Wazuh agent monitors a web server's access log (Apache, Nginx), it parses each line and makes the fields searchable in the Wazuh dashboard. This gives you endpoint-level visibility into every request that actually reached the application, complementing what SafeLine WAF sees at the perimeter.

Nginx Access Log Line (parsed by Wazuh agent)
# Raw nginx access log line 10.0.0.5 - jdoe [20/Sep/2026:10:31:07 +0000] "GET /api/users HTTP/1.1" 200 4821 "https://app.example.com/" "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" # Wazuh parses this into these fields: srcip: 10.0.0.5 id: jdoe # authenticated user if configured full_log: GET /api/users HTTP/1.1 url: /api/users http_method: GET status: 200 size: 4821 # response bytes referer: https://app.example.com/ browser: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Incident Response: SafeLine WAF vs Wazuh Web Logs
SafeLine WAF logs requests it blocked before they reached the server. Wazuh web logs record requests that made it through to the application. Comparing both sources is powerful: if SafeLine blocked an attack but you see a matching request in the Wazuh web log shortly after, the attacker may have modified their payload to bypass the WAF. Both tools complement each other.

Key Takeaways

  • HTTP is a text-based, stateless protocol. Every web attack arrives as an HTTP request. This makes HTTP log analysis fundamental to web application security.
  • HTTP requests have a method, path, headers, and optional body. Attackers put malicious payloads in the URL, query string, headers, and especially the POST body.
  • Status codes tell the story at a glance. 401 repeated then 200 = brute force success. Hundreds of 404s = directory scanning.
  • Cookies maintain session state. A stolen session cookie is as good as knowing the password. The SafeLine WAF logs the Cookie header on every request.
  • SafeLine WAF fields to know: src_ip, method, url, status_code, action, attack_type, rule_id and user_agent.
  • Wazuh agents on web servers record what actually hit the application. Comparing WAF logs and Wazuh web logs reveals WAF bypass attempts.
