Chapter 18 - Capstone

Reconstruct the Attack

Run a real 2-minute randomized flood attack against sl-ubuntu-srv01 and sl-ubuntu-srv02 using the SLCA Traffic Flood Toolkit. Detect every attack type using your full tool stack. Write a professional incident report. Nobody tells you what fired - you find it yourself.
This is a Live Exercise, Not a Reading Task
You will run real attack traffic against real targets in your lab. The toolkit randomizes which attack types it uses, so every student gets a different combination. Your job is to detect whatever actually happened using Grafana, Graylog, Wazuh, Wireshark, and SafeLine - then write a report proving what you found. There is no answer key. The logs are the answer.

What You Are Demonstrating

  • Setting up a complete pre-flight monitoring state before an attack occurs
  • Using Grafana as the first-response detection layer during a live attack
  • Querying Graylog (Sophos + SafeLine + Wazuh logs) to identify attack types and timestamps
  • Writing Wireshark display filters to confirm each attack at the packet level
  • Cross-correlating evidence across five tools to build a complete picture
  • Identifying what each tool can and cannot see for each attack type
  • Writing a professional incident report from raw evidence with no guidance

The Traffic Flood Toolkit

The SLCA Traffic Flood Toolkit is a controlled lab tool from the Shef Labs Cyber Academy GitHub repository. It is designed to generate realistic flood attack traffic against lab targets. In randomized mode it draws from a pool of attack types and runs them in sequence or in parallel for the specified duration. You do not know in advance which attacks will be selected.

Attack Pool

The toolkit draws from the following attack types. Your job is to determine which of these occurred in your run:

Attack TypeProtocol / LayerWhat it generatesPrimary tool to detect it
SYN FloodLayer 4TCP Mass TCP SYN packets to a single port without completing the handshake. Exhausts the server connection table. Sophos IPS (via Graylog) + Grafana connection count spike
UDP FloodLayer 4UDP Mass UDP packets to random ports. Forces ICMP Port Unreachable responses, saturating CPU and bandwidth. Sophos IPS (via Graylog) + Grafana network ingress spike
ICMP FloodLayer 3ICMP Mass ICMP Echo Request packets (ping flood). Saturates bandwidth and forces the host to generate Echo Reply traffic. Sophos IPS (via Graylog) + Wireshark + Grafana
HTTP FloodLayer 7HTTP Mass HTTP GET or POST requests to the web server. Exhausts web worker threads and back-end database connections. SafeLine WAF (via Graylog) + Grafana CPU spike on web server VM
TCP Port ScanLayer 4TCP SYN scan across all ports on the target. Identifies open services as a recon step before other attacks. Sophos IPS (via Graylog) + Wireshark SYN pattern
Connection ExhaustionLayer 4TCP Opens thousands of legitimate TCP connections and holds them open without sending data. Exhausts the file descriptor limit on the server. Grafana (open connection count) + Wazuh (system resource alert)
DNS Query FloodLayer 4UDP/53 Mass DNS queries to the target's DNS resolver or to an external resolver via the target network. Exhausts resolver capacity. Sophos IPS (via Graylog) + Wireshark UDP/53 volume

Part 3 - Post-Attack Detection

The attack has finished. Now work through each tool systematically. Use your T=0 timestamp and T+120 as your search window. Do not skip a tool just because you think you already found the answer - you need corroboration from at least two sources for each attack type in your report.

Step 1: Grafana - Establish the Timeline

Change the Grafana time range to cover T=0 to T=5 minutes. This shows the attack window plus a recovery period after the attack stops. Look for:

  • Which panels spiked and when exactly (use the panel cursor to get precise timestamps)
  • Which host was affected more (srv01 vs srv02 may show different patterns if the toolkit targeted them with different attacks)
  • When did metrics return to baseline (the recovery time tells you the attack ended)

Write down: the timestamp and metric name for every spike you see. This becomes your attack timeline in the incident report.

Step 2: Graylog - Sophos IPS Log Queries

Run each of these queries in order. Each one targets a specific attack type. Replace T0 and T120 with your actual timestamps.

Graylog Query - All Sophos IPS events in the attack window
log_type:IPS AND timestamp:[T0 TO T120] # Results: list of every IPS signature that fired # Key field to read: signature_msg - tells you the attack type # Also read: src_ip, dst_ip, dst_port, action (Drop/Alert)
Graylog Query - SYN Flood specifically
log_type:IPS AND signature_msg:"SYN Flood" AND timestamp:[T0 TO T120] # Expected Sophos IPS log format if SYN Flood was in your run: date=2026-09-20 time=11:28:04 log_type=IPS signature_id=28200001 signature_msg=TCP SYN Flood src_ip=10.0.3.50 # the attack source - your Kali/toolkit machine dst_ip=10.0.1.11 # sl-ubuntu-srv01 or sl-ubuntu-srv02 dst_port=80 protocol=TCP packets_per_second=24300 action=Drop
Graylog Query - UDP Flood specifically
log_type:IPS AND signature_msg:"UDP Flood" AND timestamp:[T0 TO T120]
Graylog Query - ICMP Flood specifically
log_type:IPS AND (signature_msg:"ICMP Flood" OR signature_msg:"Ping Flood") AND timestamp:[T0 TO T120]
Graylog Query - Port Scan specifically
log_type:IPS AND (signature_msg:"Port Scan" OR signature_msg:"TCP Scan") AND timestamp:[T0 TO T120]
Graylog Query - DNS Query Flood
log_type:IPS AND signature_msg:"DNS Flood" AND timestamp:[T0 TO T120] # Alternatively check for high-volume UDP/53 from the attack source: protocol:UDP AND dst_port:53 AND src_ip:10.0.3.50 AND timestamp:[T0 TO T120]

Step 3: Graylog - SafeLine WAF Queries (HTTP Flood only)

SafeLine only sees HTTP/HTTPS traffic. If your run included an HTTP flood, this is where the evidence lives. For all other attack types, SafeLine will show nothing - that is not a gap in your investigation, it is correct expected behaviour. Note it in your report.

Graylog Query - SafeLine events in the attack window
source:safeline AND timestamp:[T0 TO T120] # If HTTP flood was active, you will see entries like: { "timestamp": "2026-09-20T11:28:12Z", "src_ip": "10.0.3.50", "method": "GET", "url": "/", "attack_type": "http_flood", "action": "rate_limit", "requests_per_second": 847, "status_code": 429 } # 847 requests per second from one IP = clear HTTP flood signature

Step 4: Wazuh - Alert Review

Wazuh agents on both servers collect host-level evidence. These alerts fire from the server's own logs and kernel messages, not from the network. This means Wazuh sees the impact of the attack even when Sophos drops the traffic before it reaches the host.

Wazuh - Key rule IDs to look for in your attack window
# In Wazuh Alerts, filter by time range T0 to T120 # and filter by agent.name: sl-ubuntu-srv01 OR sl-ubuntu-srv02 # Rule IDs that fire for flood attacks: rule.id: 100200 # High inbound network traffic rate (from node metrics) rule.id: 100201 # TCP connection table near exhaustion rule.id: 100202 # Kernel: possible SYN flooding on port rule.id: 100210 # High CPU utilization sustained rule.id: 100215 # ICMP error rate spike rule.id: 31151 # Web server: high request rate (Apache/Nginx log) # Full Wazuh alert JSON structure for a SYN flood host-level detection: { "timestamp": "2026-09-20T11:28:08Z", "agent": { "name": "sl-ubuntu-srv01", "ip": "10.0.1.11" }, "rule": { "id": "100202", "description": "Kernel: possible SYN flooding on port 80", "level": 10, "groups": ["dos", "network"] }, "data": { "log_source": "/var/log/kern.log", "message": "TCP: Possible SYN flooding on port 80. Sending cookies." } }

Step 5: Wireshark - Packet-Level Confirmation

Use Wireshark to confirm each attack at the packet level. The PCAP you started before the attack contains the full evidence. Apply each filter below and check whether that traffic pattern is present.

Attack TypeWireshark Display FilterWhat you expect to see if active
SYN Flood tcp.flags.syn==1 and tcp.flags.ack==0 and ip.dst==<srv-ip> Mass SYN packets, no SYN/ACK responses completing the handshake, thousands per second
UDP Flood udp and ip.dst==<srv-ip> Mass UDP to random high ports, followed by ICMP Port Unreachable responses from the server
ICMP Flood icmp and ip.dst==<srv-ip> Mass Echo Request packets. Server replies with Echo Reply to each one. IO Graph shows a vertical spike.
HTTP Flood http.request and ip.dst==<srv-ip> Mass HTTP GET requests from the attack source, all identical or slightly varied URLs, no meaningful user agent
TCP Port Scan tcp.flags.syn==1 and tcp.flags.ack==0 and ip.src==<attacker-ip> Sequential SYN packets to ascending port numbers. Open ports: SYN/ACK back. Closed ports: RST back.
Connection Exhaustion tcp.flags.syn==1 and ip.src==<attacker-ip> then check Statistics > Conversations Many full handshakes completing but no data flowing. Hundreds of established connections with no payload.
DNS Flood dns and ip.src==<attacker-ip> Mass DNS query packets, all from attacker source, many different or repeated query names
What if a Filter Returns No Results?
That means this attack type was not in your randomized run. This is a valid finding. Write it in your report as "not observed - no evidence in Wireshark capture, Sophos IPS, or Wazuh". Negative evidence is still evidence.

Part 4 - Coverage Verification

Before writing your report, run through this cross-tool check to make sure you have not missed anything. Every spike on Grafana should have a corresponding Graylog entry and a Wireshark pattern. If they do not match, investigate the gap.

If you see this...But NOT this...Investigate this possibility
Grafana CPU spike on srv01 No matching Sophos IPS log in Graylog Attack traffic may have originated from inside the network (LAN-side of Sophos, not WAN). Check Wazuh agent logs directly. Check Wireshark for internal source IPs.
Grafana network ingress spike No Wireshark traffic matching the spike Wireshark may have been capturing the wrong interface. Check whether the interface you captured is the one receiving the flood traffic. Try filtering by the toolkit source IP.
Sophos IPS alert in Graylog No corresponding Grafana spike Sophos may have dropped the traffic before it hit the server. This is correct and expected behaviour. The attack was stopped at the perimeter - the server never saw it, so no metric spike. Note this as "blocked by Sophos before impact" in your report.
Wazuh kernel log alert No Sophos IPS event Traffic may have bypassed the perimeter (internal source) and hit the host directly. Sophos only inspects traffic crossing its interfaces.
SafeLine WAF events No Sophos IPS event for the same attack HTTP flood is a Layer 7 attack. Sophos IPS may not have fired a signature because the HTTP requests were individually valid. SafeLine's rate-based detection at Layer 7 catches what IPS signature matching misses.

The Two-Vantage-Point Principle

Your submission contains two PCAP files from two different positions in the network. Together they tell the complete forensic story of the attack.

Capture SourceVantage PointWhat it provesWhat it cannot show
Kali (Wireshark, attacker side) The source - traffic as it leaves the attack machine Exactly which attack types were sent, to which targets, at what times. The ground truth of what was attempted. Whether Sophos dropped the traffic. Whether it reached the server. Server-side impact.
sl-ubuntu-srv01 (Wireshark, defender side) The destination - traffic as it arrives at the target Which attacks broke through Sophos and reached the server. The actual impact on the host. Attack types that Sophos dropped before they hit the server - these will be in the Kali PCAP but not here.

When a Sophos IPS alert appears in Graylog but there is no matching traffic in the server-side Wireshark capture, this is evidence that Sophos successfully blocked the attack. The Kali-side PCAP confirms the attack was sent. The absence of that traffic in the server-side PCAP confirms Sophos stopped it. Both facts belong in your report.

Why Both PCAPs Are Required
Either PCAP alone is incomplete evidence. The Kali PCAP without a server-side capture does not prove the attack reached the target. The server-side capture without the Kali PCAP does not prove who sent the attack or when. Together they form a chain of custody from attacker to target - exactly what a professional forensics report requires.

Course Complete

  • You ran a real attack toolkit against real targets and found the evidence without being told what happened. That is the core skill of a Tier-1 analyst.
  • Grafana gives you the fastest signal during a live attack. It tells you something is happening before the logs have been processed. Use it to establish your timeline first.
  • Graylog is your central investigation point. All Sophos IPS, SafeLine WAF, and Wazuh alerts converge there. A time-bounded Graylog query against a known attack window is how you systematically audit what happened.
  • Wireshark provides packet-level proof. Every claim in your incident report should have a corresponding Wireshark filter and packet count backing it up.
  • SafeLine WAF is only relevant for Layer 7 HTTP/HTTPS attacks. For every other attack type in this exercise, its absence from the logs is correct expected behaviour, not a gap.
  • Correctly identifying what did NOT happen is equally important to identifying what did. Negative evidence belongs in the report.
  • An incident report is a chain of evidence. Timestamp, tool, field name, field value - every claim must be traceable to a specific log entry or packet.
