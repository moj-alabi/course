Chapter 06

Reading the Browser

User-Agent, Origin, Referer, Sec-Fetch headers, and CORS. How SafeLine WAF uses these to distinguish legitimate browsers from attack tools, scanners, and bots.

Learning Objectives

  • Explain what the User-Agent header reveals and how attackers manipulate it
  • Describe the purpose of the Referer and Origin headers
  • Understand what the Sec-Fetch-* headers tell a server about the browser security context
  • Explain what CORS is, why it exists, and what a CORS pre-flight request looks like
  • Identify browser header anomalies in SafeLine WAF logs that indicate tool-based attacks
  • Read a realistic SafeLine WAF log entry and extract attacker fingerprint information

The User-Agent Header

Every HTTP request sent by a browser includes a User-Agent header. This header identifies the software making the request: the browser name, version, operating system, and rendering engine. The server can use this to tailor responses, but defenders use it to fingerprint who is really making requests.

Legitimate browsers send specific, well-formatted User-Agent strings. Attack tools like sqlmap, nikto, gobuster, and masscan send their own identifying strings by default, or sometimes generic/blank ones. Spotting these in logs is one of the quickest ways to identify automated attack traffic.

User-Agent Header: Legitimate Browser vs Attack Tools
Legitimate browsers follow a consistent User-Agent format. Attack tools typically identify themselves explicitly or use obviously non-browser strings.
Attackers Can Fake User-Agents
Any attacker can change their User-Agent to look like a legitimate browser. A sophisticated attacker will always do this. A User-Agent that looks legitimate does not mean the request is benign. You need to use multiple signals together. However, when you see a tool name in the User-Agent, that is reliable evidence because the attacker simply forgot to change it.

Referer and Origin Headers

Referer

The Referer header tells the server which page the user came from when they made the current request. For example, if you click a link on https://search.example.com that takes you to https://shop.example.com/product, the request to the shop will include Referer: https://search.example.com.

For defenders, missing or anomalous Referer values are useful signals. A POST to a login endpoint with no Referer may indicate a scripted attack rather than a browser interaction. A Referer pointing to an external domain on a sensitive internal request could indicate cross-site request forgery (CSRF).

Origin

The Origin header is similar to Referer but includes only the scheme, hostname, and port, without the path. It is sent on cross-origin requests (requests to a different domain) and on all requests made by JavaScript using fetch() or XMLHttpRequest. It is more precise than Referer and harder to accidentally leak sensitive paths.

Sec-Fetch Headers: The Browser Security Context

Modern browsers send a set of Sec-Fetch-* headers on every request. These headers describe the security context of the request: what caused it, where it is going, and what kind of content is expected. Unlike User-Agent or Referer, these headers cannot be set by JavaScript running in a web page (they are forbidden headers), which makes them reliable fingerprinting signals.

Attack tools that directly forge HTTP requests will not include these headers, or will include incorrect values. This makes Sec-Fetch headers one of the best ways to distinguish genuine browser requests from scripted attacks at the WAF layer.

Sec-Fetch Headers - What They Mean
Sec-Fetch headers are set by the browser and cannot be overridden by page scripts. They are reliable indicators of whether a request came from a real browser.

CORS: Cross-Origin Resource Sharing

By default, a browser will not allow a script on one domain to read responses from a different domain. This security policy is called the Same-Origin Policy. It prevents a malicious website from silently reading your bank account data by making requests to your bank's API while you are logged in.

CORS (Cross-Origin Resource Sharing) is the controlled mechanism for relaxing the Same-Origin Policy. A server can tell the browser "requests from these specific origins are allowed" by including Access-Control-Allow-Origin headers in its responses.

CORS Pre-Flight Request Flow
A CORS pre-flight is an OPTIONS request the browser sends automatically before a cross-origin POST or PUT. The server must respond with the correct allow headers or the browser will block the actual request.

What a Browser Anomaly Looks Like in SafeLine WAF Logs

When SafeLine detects a request that does not look like it came from a real browser, it can flag or block it based on missing headers, suspicious User-Agent strings, or unusual header combinations.

SafeLine WAF - Blocked Bot / Scanner Request
{ "timestamp": "2026-09-20T11:04:22.009Z", "src_ip": "185.220.101.45", "method": "GET", "host": "shop.example.com", "url": "/wp-admin/admin-ajax.php", "status_code": 403, "action": "block", "attack_type": "scanner", "user_agent": "python-requests/2.31.0", "sec_fetch_site": "absent", "sec_fetch_mode": "absent", "accept": "*/*", "accept_language": "absent", "referer": "absent" }
Incident Response: Fingerprinting the Attacker
The log above tells you: (1) the source IP is 185.220.101.45 which is a Tor exit node - check it against threat intel, (2) the tool is python-requests which means a custom script, not a known tool, (3) the target path /wp-admin/admin-ajax.php is a WordPress admin path - this host may not even run WordPress, suggesting automated scanning, (4) no Sec-Fetch headers means it is definitely not a browser. Open a ticket, look up that IP, and check whether any other internal hosts communicated with it.

Key Takeaways

  • The User-Agent header identifies the software making a request. Attack tools often reveal themselves through their User-Agent string. However, sophisticated attackers fake it, so never rely on User-Agent alone.
  • Referer tells you where the user came from. Origin is sent on cross-origin JavaScript requests. Anomalies in either can indicate CSRF or scripted attacks.
  • Sec-Fetch headers are set by the browser and cannot be forged by page scripts. Missing Sec-Fetch headers on a web request is a reliable indicator of a non-browser client.
  • CORS controls which external origins can read cross-origin responses. A wildcard Access-Control-Allow-Origin setting is a significant security misconfiguration.
  • In SafeLine WAF logs, combine user_agent, sec_fetch_site, accept_language, and referer to build a reliable picture of whether a request came from a real user or an automated tool.
